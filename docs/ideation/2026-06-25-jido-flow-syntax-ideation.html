Evidence Base

Grounding Context

Jido.Flow already has the right architecture for careful syntax growth: macro DSL, parser, and runtime builder emit shared syntax and lower through Jido.Flow.Syntax.Lowerer into canonical %Jido.Flow{}. The semantic artifact is small: named action nodes, ref-based inputs, derived deps, one return ref, and non-semantic provenance.

The main implementation constraint is that the current compiler topologically orders nodes but then chains every Runic step through the previous step. That means syntax can safely expose better authoring, projection, provenance, and graph intent now, but it must not promise real parallel execution until compilation uses the dependency graph directly.

Runic supports the larger future: DAG execution, joins, fan-out/fan-in, runtime context, scheduler policy, async execution, and runner durability. Those should influence the language shape, but Flow should not collapse all of them into inline workflow policy syntax.

1

Binding-First Script Spine

Confidence 88%Complexity Medium
Axis
Authoring parity and script ergonomics
Description
Make the primary readable form quote = step :price_cart, PriceCart, with: ..., then use return quote or select(quote, :total). The handle is source-level sugar over Ref.result(:price_cart); it disappears from semantic maps and can survive only as provenance/debug metadata. This absorbs with: into a larger script spine instead of treating it as the feature.
Basis
direct: the brief already shows assignment plus with: in its desired DX, names variable binding as a core operation, and the current tests explicitly reject bind/var forms for now.
Rationale
This is the highest-leverage syntax move because every later feature is easier to read when prior results have handles instead of repeated result(:node, path) calls.
Downsides
Parser support must remain an allowlisted AST subset, and assignment must not imply arbitrary Elixir variables or runtime evaluation.
2

Projection-Only Data Shaping

Confidence 86%Complexity Medium
Axis
Expression and data shaping
Description
Add select(ref, path) and shape(...) as the only blessed projection and payload-building primitives. They lower to existing refs, maps, lists, and literals. They do not support transforms, predicates, arithmetic, captures, or arbitrary calls.
Basis
direct: the brief calls out select and shape; the lowerer and compiler already resolve nested maps/lists and path refs recursively; the brief warns against creating a general expression language.
Rationale
Most real Flow code will be action-param wiring. A projection-only shaping layer gives authors a clear vocabulary while preserving the boundary that business logic belongs in actions.
Downsides
The team must decide whether raw maps remain idiomatic or whether shape becomes the preferred style. Return shaping should not silently become a general expression evaluator.
3

Explicit Graph Edges

Confidence 82%Complexity Medium
Axis
Dependency graph and Runic semantics
Description
Expose non-data dependency edges with after: or depends_on:, e.g. step :audit, Audit, with: %{id: input(:id)}, after: [:charge]. Pair this with a later graph-first authoring decision: collect all nodes, then validate refs and topologically order them instead of forcing all result refs to point backward in source order.
Basis
direct: canonical nodes already have explicit deps, and Node.result_deps/1 combines explicit deps with inferred result refs. The lowerer simply does not expose explicit deps today.
Rationale
It prevents fake data dependencies and makes the artifact's graph intent inspectable before the compiler gains true graph-shaped Runic construction.
Downsides
Forward refs and explicit deps shift validation timing. Error messages must remain source-aware and parity-tested across macro, parser, and builder.
4

Honest Branch Grouping

Confidence 73%Complexity Medium
Axis
Dependency graph and Runic semantics
Description
Use terms like lane, group, or possibly independent to describe branch readability and graph intent before promising runtime parallel. A grouping block should initially lower to ordinary nodes/deps plus provenance, or act as a structural assertion that branches are independent.
Basis
direct: current compiler tests deliberately serialize independent branches; the brief says parallelism should be a property of dependency graph and Runic execution, not necessarily a canonical grouping entry.
Rationale
The name chosen here sets user expectations. Calling something parallel while the compiler chains every step through previous_name would damage trust.
Downsides
Grouping syntax may be weak if it is only provenance. It earns its place when paired with explicit deps and later graph-shaped Runic compilation.
5

Flow-Visible Runtime Context Contract

Confidence 60%Complexity Medium
Axis
Execution policy boundaries
Description
Explore context(:trace_id) as a read-only data source and/or requires_context [:tenant_id] as a contract declaration. This is explicitly not scheduler policy, retry behavior, or durability. It is about making selected runtime dependencies visible in the artifact.
Basis
direct: Jido.Exec.run/3 already separates input and context, and Flow.Compiler carries context to actions. external: Runic has runtime context that is not part of workflow hash or serialized facts.
Rationale
Developers will need to decide whether context remains purely action-private ambient data or whether Flow can name required external pins without embedding their values.
Downsides
This requires a new ref kind or contract field, and it raises security questions around making context keys visible. It should stay separate from policy syntax.
6

Provenance-Only Plan Annotations

Confidence 78%Complexity Low
Axis
Parser/provenance safety
Description
Add label:, tags:, note, and source-span provenance for explanation, diagnostics, visualization, and future external policy selection. These annotations are omitted from semantic maps unless provenance: true is requested.
Basis
direct: syntax operations, nodes, and flows already have provenance fields, and Flow.to_map/2 omits provenance by default.
Rationale
Flow is justified as an inspectable artifact. Annotation support can make it substantially easier to understand without increasing execution semantics.
Downsides
Low semantic risk, but easy to overdo. Keep it useful for errors, diagrams, and future selectors rather than turning it into doc-comment sprawl.
7

Parser-Safe Stored Source Profile

Confidence 80%Complexity Medium-High
Axis
Parser/provenance safety
Description
Keep the Elixir-like DSL as trusted developer syntax, but define a safer profile for stored or user-edited text: registered action identifiers, existing atoms only, or string step IDs resolved through a registry. This may become a separate manifest-style surface rather than stretching the trusted parser too far.
Basis
direct: the parser is currently documented as trusted developer input and the brief calls out atom-heavy parsed text as a safety risk for arbitrary user-submitted source.
Rationale
This prevents a future trap where the same syntax tries to be both ergonomic Elixir-like authoring and safe untrusted input.
Downsides
Higher complexity and not needed for the immediate macro DSL. It matters if Flow source is meant to be stored, edited, or accepted from outside trusted code.

Deliberate Gap

No survivor proposes immediate true parallel execution. That is intentional: Runic supports the necessary graph machinery, but the current Flow compiler serializes nodes. Syntax should first expose graph intent honestly.
